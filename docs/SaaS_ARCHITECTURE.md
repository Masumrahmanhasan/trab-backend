# SaaS Backend Architecture

Enterprise-scale Laravel multi-tenant SaaS: stores as tenants, namespaced RBAC,
a plan/feature capability system, fully in-system subscription & trial handling,
and a post-launch mechanism for shipping new features to existing subscribers.

## 1. Tenets

- **No payment processor.** Subscriptions are first-class rows in `subscriptions` and are managed entirely by the platform.
- **No try/catch for flow control.** Domain rules are enforced by throwing `InvalidArgumentException` (mapped to HTTP 400) and by database transactions, not by catching exceptions in controllers.
- **Config is the source of truth.** Permissions, roles, features and plans are declared in `config/permissions.php` and materialised by seeders. Code never hard-codes permission keys.
- **Namespaced keys.** Every permission is `<context>.<resource>.<action>`; the `context` column (`platform` | `store`) separates the SaaS-owner panel from merchant tenants so a store role can never grant platform access.

## 2. Multi-tenancy

**The tenant is the store.** A user can own many stores (subject to `plan.max_stores`).

### Schema

- `stores.owner_id` → the merchant account.
- `stores.plan_id` → the account plan at the time of assignment (mirrors the owner's subscription plan).
- Role/permission grants are scoped by a `team_id` pivot column on `model_has_roles` and `model_has_permissions`. `team_id = null` means a **global (platform)** grant; `team_id = N` means a **grant scoped to store N**.

### Request-time context

`SetTeamContext` middleware (`app/Http/Middleware/SetTeamContext.php`, alias `set.team.context`) resolves the active store from, in order:

1. the route's `{store}` parameter,
2. the `X-Team-Id` header,
3. the `team_id` query parameter.

It calls `$user->setTeamId($storeId)`, which is read by `hasRole()`, `hasPermissionTo()`, `assignRole()` and `assignPermissionTo()` whenever no explicit team id is passed.

### Scoping semantics

- `User::hasPermissionTo($key)` / `hasRole($key)` with **no** team context only considers grants where `team_id IS NULL` (global/platform). Store-scoped grants require an explicit store id.
- `User::permissionsInTeam($teamId)` / `rolesInTeam($teamId)` return the grants scoped to one store.
- Staff belong to a store via scoped roles/permissions, never via `stores.owner_id`.

## 3. Permissions & Roles

### Permission keys

```
platform.users.view       platform.system.manage        (SaaS-owner panel)
store.products.manage     store.orders.export           (merchant tenant)
```

Keys are generated by `PermissionsTableSeeder` from `config('permissions.contexts')`, plus an `extra` map for cross-resource actions (e.g. `platform.roles.assign`, `store.permissions.assign`).

### Contexts

- `platform.*` — the super-admin panel. Only users with the `super-admin` role reach it (`superadmin` middleware checks `hasRole('super-admin')`).
- `store.*` — tenant application. Granted to store owners via the `owner` role and to staff via scoped roles/direct grants.

### Built-in roles (`config('permissions.roles')`)

| Role | Context | Permissions |
|------|---------|-------------|
| `super-admin` | platform | every `platform.*` permission |
| `user` | platform | none (the default role every account gets) |
| `owner` | store | every `store.*` permission |
| `manager` | store | explicit list (orders, products, customers, invoices, staff view, reports) |
| `staff` | store | view-only list |

The `super-admin` and `owner` roles are granted every permission in their context **by design**; they use the reserved tokens `platform` / `store` in the config instead of a maintenance-heavy list.

### Enforcement points

- `StorePolicy` (`app/Policies/StorePolicy.php`) gates store routes; it is registered in `AppServiceProvider`.
- `StoreController` uses `$this->authorize(...)` (the `AuthorizesRequests` trait must be present — it was missing).
- The `superadmin` middleware (`IsSuperAdmin`) guards the `/api/v1/super-admin/*` group.

## 4. Features & Plans

Features are **plan capabilities**. They sit one level above permissions:

```
Plan --(plan_feature, is_trial_allowed)--> Feature --(permission_key)--> Permission
```

- Each feature **may** carry a `permission_key`. When it does, granting the feature materialises that permission.
- A feature with `permission_key = null` is a pure capability flag (`multi-store`), enforced through `plan.max_stores` and `plan.max_staff_per_store` rather than the RBAC system.
- The `plan_feature` pivot stores `is_trial_allowed` so trial subscribers only receive the subset of a plan's features that are enabled for trials.

### The three seeded plans

| Plan | Price | Stores | Staff/store | Trial | Feature highlights |
|------|-------|--------|-------------|-------|--------------------|
| `default` | 0 | 1 | 2 | 14d | store, product, customer management |
| `starter` | 29 | 2 | 5 | 14d | + orders, staff, multi-store (invoice/reports off during trial) |
| `pro` | 99 | 10 | 25 | 14d | all features |

`default` is flagged `is_default = true`; `Plan::default()` is used when a new account signs up.

## 5. Subscriptions & Trials

### Model

`subscriptions` rows carry `user_id`, `plan_id`, optional `store_id`, a string `status`, `starts_at`, `ends_at`, `trial_ends_at`, and billing fields. `User::activeSubscription` is the current one (latest, non-terminal).

### Lifecycle (`SubscriptionService`)

- **Registration** (`AuthenticationService::registerWithSubscription`) auto-creates a subscription on the default plan and starts its trial (`SubscriptionStatus::TRIALING`). The user receives the default `user` role and only the trial-enabled feature permissions.
- **Create** (`createSubscription`) starts a trial when the plan has `trial_days`, otherwise an active paid period. `canSubscribe()` rejects users who already hold a current subscription or exceed the plan's store count.
- **Change plan** (`changePlan`) requires a current subscription, switches `plan_id`, recomputes `ends_at`, **mirrors the new plan onto every owned store**, and re-materialises permissions.
- **Cancel / resume / renew / expire** transition the status machine and grant/revoke access (see §6–7).

### Trial enforcement

`CheckSubscription` middleware (alias `subscription`) inspects `$user->activeSubscription` and requires `isActive() || isOnTrial()`. The hourly `subscriptions:check-expiry` job flips overdue trials/periods to `expired` and tears down grants.

## 6. Subscription lifecycle state machine

```
              register (default plan)
                    |
                    v
                PENDING
                    |
              trial_days > 0?
              /            \
            yes             no
             |               |
             v               v
        TRIALING  ----(trial ends / check-expiry)---->  EXPIRED
             |                                            |
             +------ plan change/upgrade ------->  ACTIVE  |
                      |                           ^       |
                      |                           |       |
                      +------ resume <---- CANCELLED ----+
                                        ^
                                        |
                     cancel (from ACTIVE or TRIALING)
```

- `ACTIVE` and `TRIALING` are "current"; `CANCELLED` and `EXPIRED` are terminal.
- `cancel()` keeps the subscription usable until `ends_at` but stops plan-derived access re-syncs; `resume()` is allowed only from `CANCELLED`; `renew()` only from `EXPIRED`.

## 7. Permission materialisation (`PermissionSyncService`)

Plans are not checked live on every request; their effect is **materialised into grants** so the existing custom RBAC (`model_has_roles` / `model_has_permissions` with `team_id`) keeps working unchanged.

- **Global (platform) features** → direct permissions on the user (`syncPermissions`), filtered by trial via `is_trial_allowed`.
- **Store features** → the owner is given the `owner` role scoped to the store plus direct store-scoped permissions for the plan's features (`StoreOnboardingService::assignPlanPermissionsToOwner`).
- **Teardown** — `cancelSubscription` / `expireSubscription` call `revokeGlobalPlanPermissions` (removes `team_id IS NULL` platform grants) and `revokeStoreAccess` per owned store (removes scoped roles + permissions).
- **`resyncAllCurrentSubscribers`** re-runs materialisation for every user with a current subscription — the engine behind `features:sync`.

Manually granted staff permissions are preserved across plan changes because only the **owner's** grants are re-materialised.

## 8. Seeding

`DatabaseSeeder` runs in dependency order; every seeder is **idempotent** (upsert by natural key), so re-running is safe:

1. `PermissionsTableSeeder` — generates `<context>.<resource>.<action>` keys from config.
2. `RolesTableSeeder` — creates roles and syncs `role_has_permissions`.
3. `FeaturesTableSeeder` — upserts features.
4. `PlansTableSeeder` — upserts plans and syncs `plan_feature` with `is_trial_allowed`; enforces a single `is_default`.
5. `UsersTableSeeder` — creates the super admin (full platform role + subscription) and a demo user (default `user` role + default-plan trial). Credentials come from `config('permissions.*')` / env.

## 9. Adding a feature after launch

`php artisan features:sync` (`app/Console/Commands/SyncFeatures.php`) is the supported mechanism:

1. Declare the new resource/actions under the right context in `config/permissions.php`.
2. Add a feature entry under `'features'`.
3. Link it to plans under `'plans'` (and decide `is_trial_allowed`).
4. Run:

   ```
   php artisan features:sync
   ```

The command re-runs the four RBAC seeders silently, then calls `PermissionSyncService::resyncAllCurrentSubscribers()` so existing trialing/active subscribers immediately receive the new feature's permissions — no data migration, no code deploy.

## 10. Error handling conventions

- `InvalidArgumentException` for domain/validation-of-state failures → HTTP **400** with the exception message (registered as a JSON renderable in `bootstrap/app.php`).
- `ValidationException` → HTTP **422** with Laravel's conventional `{ message, errors }` shape.
- All state-changing service methods wrap their work in `DB::transaction`; nothing is half-applied.
- **No try/catch in flow paths** — controllers call services, and the exception handler converts domain exceptions to API responses.

> Note: `app/Exceptions/Handler.php` is not used. `bootstrap/app.php` calls `withExceptions(...)`, which binds the framework handler and registers the renderables shown above. Keep exception configuration in `bootstrap/app.php`.

## 11. Scheduling

Defined in `routes/console.php`:

| Schedule | Command | Purpose |
|----------|---------|---------|
| hourly | `subscriptions:check-expiry` | expire overdue trials/periods, revoke grants |
| daily 09:00 | `subscriptions:send-reminders` | notify users whose subscription expires within 7 days |

## 12. Directory map

```
config/permissions.php                     Single source of truth (contexts, roles, features, plans)
app/Enums/                                 SubscriptionStatus, Roles, PermissionContext, StoreStatus, ...
app/Models/Concerns/                       HasRoles, HasPermissions, HasTeamContext (custom RBAC, no package)
app/Services/PermissionSyncService.php     Plan/feature -> permission materialisation + teardown
app/Services/SubscriptionService.php       Subscription & trial lifecycle
app/Services/StoreOnboardingService.php    Store creation, owner grants, store limits
app/Services/AuthenticationService.php     Registration + auto trial subscription
app/Http/Middleware/SetTeamContext.php     Tenant resolution (route store / X-Team-Id / team_id)
app/Http/Middleware/CheckSubscription.php  Trial/active gate
app/Http/Middleware/IsSuperAdmin.php       SaaS-owner panel gate
app/Http/Controllers/Api/V1/               Registration, profile, plans, features, subscriptions, stores, super-admin
database/seeders/                          Idempotent, config-driven seeders
app/Console/Commands/SyncFeatures.php      features:sync — the post-launch feature rollout
routes/api.php                             Versioned API surface (v1)
```
